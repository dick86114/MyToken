# 更新日志与 Issue 提交设计

## 目标

为更新检查、下载、安装和自动重启失败提供可诊断日志，并让用户能够通过应用内入口打开预填充日志的 GitHub Issue 页面，降低问题反馈成本，同时避免上传本地 Key 或其他敏感信息。

## 方案

### 本地日志

- 新增 `AppLogStore`，将结构化事件追加到 `~/Library/Logs/MyRoutin/app.log`。
- 日志记录时间、事件级别、事件名称和简短详情。
- 更新链路记录请求开始、HTTP 状态码、API 限流回退、解析失败、下载进度结果、安装结果和自动重启结果。
- 写入前统一脱敏：匹配 `plan-` 凭据、URL 查询参数中的敏感字段，以及过长的自由文本。
- 日志文件只保留有限大小；生成 Issue 时只取最近日志，限制 URL 长度。
- 文件写入失败不影响正常更新流程，只记录到系统 `Logger` 并继续执行。

### Issue 生成

- 新增 `IssueReporter`，负责收集环境信息、当前更新状态和脱敏日志。
- 使用 GitHub `issues/new` 页面 URL 的 `title` 和 `body` 查询参数生成预填 Issue。
- 不在客户端内置 GitHub Token，也不直接调用创建 Issue API。
- 通过 `NSWorkspace` 打开默认浏览器；打开失败时由界面提示用户复制信息或稍后重试。

### 入口

- 菜单栏右键菜单增加“提交问题”。
- 设置页“软件更新”区域增加“提交问题”按钮。
- 两个入口共用 `IssueReporter`，保证日志内容和隐私处理一致。

## 数据流

1. `GitHubUpdateService` 或 `AppEnvironment` 产生更新事件。
2. `AppLogStore` 脱敏并追加本地日志。
3. 用户点击“提交问题”。
4. `IssueReporter` 读取最近日志，附加版本、系统版本、架构和当前更新状态。
5. 应用打开 GitHub 新 Issue 页面，用户确认后提交。

## 隐私与限制

- 不读取或上传 KeyRepository 中的秘密值。
- 不上传完整日志文件；Issue 正文只包含有限长度的最近日志。
- 只打开 GitHub 页面，不代表 Issue 已提交，最终提交由用户确认。
- 日志中只保留诊断所需的状态码、错误类型和阶段信息，不记录请求正文或响应正文。

## 测试

- 日志写入、轮转和脱敏测试。
- Issue 标题、正文、URL 编码和长度限制测试。
- 更新失败路径会生成日志事件的测试。
- 菜单栏右键菜单和设置页入口接入测试。
- 全量单元测试与 Release DMG 构建验证。
